# paraegis / CrownOps Team Rules

작성일: 2026-07-07  
기준 자료: 2026-06-24 회의 녹음본, 팀 정리본, 기존 paraegis / CrownOps 대화 맥락

## 0. 문서 목적

이 문서는 paraegis가 CrownOps를 만들고 검증하는 과정에서 팀이 같은 기준으로 일하기 위한 내부 운영 규칙이다.

핵심 목적은 세 가지다.

1. 팀의 미션, 비전, 제품 방향을 한 문서로 고정한다.
2. 두 명 체제에서 역할, 의사결정, 피드백 방식을 명확히 한다.
3. 출퇴근, 회고, 커뮤니케이션, 실행 마일스톤을 실제 운영 규칙으로 만든다.

이 문서는 완성된 사규가 아니라, 초기 스타트업 팀의 실행 헌장이다. 제품 검증, 파트너 기공소 확보, MVP 개발 단계에 맞춰 매주 업데이트할 수 있다.

paraegis는 `para`와 `aegis`를 결합한 팀명이다.

| 요소 | 의미 |
| --- | --- |
| para | 곁에서 보조하다, 보호하다, 방어하다 |
| aegis | 방패, 수호, 보호막 |
| paraegis | 실무자의 곁에서 오류와 부담을 막아주는 운영 보호막 |

팀명 의미는 다음과 같이 정리한다.

> paraegis는 의료 현장의 실무자 곁에서 정보 누락, 불일치, 책임 부담을 줄이는 운영 기술 팀입니다.

## 2. 미션과 비전

### 2.1 내부 미션

> 의료 현장에서 책임과 실무 부담을 떠안는 비의사 전문직이 더 안전하고 효율적으로 일할 수 있도록 돕는다.

이 미션은 단순히 프로그램 하나를 만드는 것을 넘어선다. 치과기공사처럼 의료 생태계 안에서 중요한 실무를 담당하지만, 정보 불일치, 책임 부담, 갑을 관계, 수동 확인 업무를 떠안는 전문직의 업무 환경을 기술로 개선하는 것이 팀의 장기적 문제의식이다.

### 2.2 외부 표현용 미션

> paraegis는 의료 현장의 의뢰 기반 업무에서 정보 누락과 불일치를 줄여, 실무자가 더 안전하고 효율적으로 일할 수 있는 운영 인프라를 만듭니다.

대외적으로는 특정 직역과 대립하는 방식으로 말하지 않는다. 핵심은 누군가와 싸우는 것이 아니라, 복잡한 협업 구조에서 실무자의 부담과 오류를 줄이는 것이다.

### 2.3 비전

> CrownOps를 시작으로 치과기공소의 제작 전 검증 표준을 만들고, 이후 의료 현장의 의뢰 기반 협업 문제를 해결하는 운영 인프라로 확장한다.

### 2.4 미션과 제품의 연결

| 구분 | 내용 |
| --- | --- |
| 큰 문제 | 의료 현장에는 정보 비대칭, 책임 전가, 수동 확인, 반복 재문의가 존재한다. |
| 첫 시장 | 치과기공소는 의뢰서, STL 파일, 재료, 쉐이드, 임플란트 정보가 여러 채널로 들어와 제작 전 오류가 발생한다. |
| 첫 제품 | CrownOps는 CAM 투입 전 제작 가능 여부를 검증한다. |
| 첫 가치 | 기공소가 제작 전 확인 업무를 줄이고, 리메이크와 납기 지연, 거래처 신뢰 손상을 예방하도록 돕는다. |
| 장기 확장 | 치과기공 이후에도 의료 현장의 의뢰 기반 업무, 검증 업무, 책임 분산 문제로 확장한다. |

## 3. 제품 원칙

### 3.1 제품 정의

> CrownOps는 치과기공소가 CAM 투입 전에 정식 의뢰서, STL 파일, 재료 조건, 쉐이드, 임플란트 정보를 확인해 “바로 제작 가능”과 “검증 필요” 케이스를 구분하는 제작 전 검증 SaaS입니다.

더 짧게 말하면 다음과 같다.

> 기존 서비스가 접수와 관리를 돕는다면, CrownOps는 제작 직전에 이 케이스를 지금 만들어도 되는지 확인합니다.

### 3.2 CrownOps가 아닌 것

| 구분 | 입장 |
| --- | --- |
| ERP | 아님 |
| MES | 아님 |
| 전자 의뢰서 플랫폼 | 아님 |
| OCR 솔루션 | 핵심 아님 |
| 청구/정산 프로그램 | 아님 |
| CAD/CAM 자동화 도구 | 아님 |
| 주문 플랫폼 | 아님 |
| 리메이크율 대시보드 | 핵심 아님 |
| 제작 전 검증 체크게이트 | 맞음 |

### 3.3 핵심 기능

| 기능 | 설명 |
| --- | --- |
| 의뢰서 확인 | 정식 의뢰서가 있는 케이스인지 확인 |
| STL 파일 확인 | STL 파일 도착 여부, 중복 여부, 누락 여부 확인 |
| 의뢰서-STL 매칭 | 환자명, 치아번호, 케이스 정보 기준으로 매칭 |
| 재료 검증 | 지르코니아, E-max 등 제작 재료 정보 누락 확인 |
| 쉐이드 검증 | 쉐이드 정보 누락 또는 불명확 케이스 표시 |
| 임플란트 정보 확인 | 스캔바디, fixture, abutment 관련 정보 부족 여부 확인 |
| 외부 검증 요청 | 치과 또는 외부 파트너에게 확인 필요한 케이스 분리 |
| 최종 확인 요청 | 소장 또는 책임자 확인이 필요한 케이스 분리 |
| 제작 가능 상태 표시 | 바로 제작 가능과 검증 필요를 구분 |

## 4. 팀 운영 원칙

### 4.1 두 명 체제의 기본 원칙

현재 팀은 두 명 체제로 운영된다. 두 명 체제에서는 한 사람의 침묵이 의사결정의 공백으로 이어질 수 있다. 따라서 각자는 자신의 역할뿐 아니라, 팀의 방향에 대한 의견을 분명히 말해야 한다.

| 항목 | 원칙 |
| --- | --- |
| 대표/파운더 역할 | 미션, 비전, 제품 방향을 명확히 말하고 팀원을 설득한다. |
| 팀원 역할 | 단순 동의자가 아니라 자기 의견을 적극적으로 제시한다. |
| 의사결정 | 한 명이 정하고 한 명이 따르는 구조가 아니라, 방향 제시와 반론을 거쳐 결정한다. |
| 갈등 인식 | 의견 충돌은 팀의 문제가 아니라 좋은 결정을 위한 과정으로 본다. |
| 최종 기준 | 고객 검증, 실행 가능성, 팀 미션과의 일치도를 기준으로 결정한다. |

### 4.2 커뮤니케이션 톤

| 구성원 | 보완할 점 |
| --- | --- |
| 대표/파운더 | 더 차분하고 섬세하게 말한다. 강한 문제의식은 유지하되, 상대가 방어적으로 느끼지 않게 전달한다. |
| 팀원 | 중재자 역할에만 머무르지 않고, 반대 의견과 대안을 더 적극적으로 제시한다. |

팀 안에서는 다음 문장을 기본 태도로 둔다.

> 우리는 서로를 설득할 책임이 있고, 납득되지 않은 동의는 좋은 실행으로 이어지지 않는다.

### 4.3 피드백 원칙

| 원칙 | 설명 |
| --- | --- |
| 빠르게 말하기 | 불만이나 불편함은 쌓아두지 않고 빠르게 말한다. |
| 행동 중심으로 말하기 | 성격 평가가 아니라 관찰된 행동과 영향 중심으로 말한다. |
| 대안까지 제시하기 | 문제 제기만 하지 않고, 원하는 방식이나 대안을 함께 말한다. |
| 방어보다 이해 | 피드백을 들을 때 즉시 반박하기보다 먼저 의도를 확인한다. |
| 결정 후 헌신 | 충분히 논의한 뒤 결정되면, 개인 의견과 달라도 실행에는 헌신한다. |

피드백 문장 템플릿은 다음과 같다.

```text
내가 보기에는 [상황]에서 [행동/방식] 때문에 [영향]이 생기는 것 같아.
나는 다음부터 [대안]으로 해보면 좋겠어.
네 생각은 어때?
```

## 5. 역할과 책임

### 5.1 기본 역할

| 역할 | 주요 책임 |
| --- | --- |
| 대표/Project Lead | 미션/비전 정렬, 외부 네트워크, 교수/학회 연결, 발표자료, 파트너십 전략 |
| Tech/Execution Lead | MVP 구현, 기공소 컨택, 제품 요구사항 정리, 현장 피드백 반영, 실행 일정 관리 |

역할은 고정된 직무가 아니라 현재 단계의 우선순위다. 초기에는 제품 검증과 파트너 확보가 가장 중요하므로, 두 명 모두 영업, 인터뷰, 자료 제작, 제품 기획에 함께 관여한다.

### 5.2 의사결정 방식

| 의사결정 유형 | 방식 |
| --- | --- |
| 미션/비전 | 충분히 토론하고, 대표가 최종 문장화한다. |
| 제품 범위 | 고객 검증 결과와 개발 가능성을 기준으로 합의한다. |
| 일정/마감 | 실행 담당자가 현실성을 제시하고, 둘이 데드라인을 확정한다. |
| 외부 메시지 | 대외 리스크가 있으므로 공격적 표현은 줄이고, 실무자 부담 완화 중심으로 정리한다. |
| 긴급 결정 | 24시간 안에 답이 필요하면 담당자가 임시 결정하고, 이후 회고에서 조정한다. |

### 5.3 결정 기록

중요한 결정은 반드시 기록한다.

| 기록 대상 | 예시 |
| --- | --- |
| 제품 범위 변경 | “OCR은 핵심 기능에서 제외하고 제작 전 검증에 집중한다.” |
| 고객 인터뷰 결과 | “파일 누락/불일치 방지가 1순위로 확인됨.” |
| 일정 변경 | “주말 상시 근무에서 발표 전주 중심 근무로 조정.” |
| 외부 컨택 | “누구에게 언제 어떤 자료를 보냈고, 다음 액션은 무엇인지.” |

## 6. 출퇴근 및 근무 규칙

### 6.1 기본 출퇴근 시간

| 요일 | 출근 | 퇴근 |
| --- | --- | --- |
| 월-금 | 13:00 | 최소 21:00 |

| 일요일 | 기본 휴무 |

### 6.2 주말 근무 원칙

주말 근무는 “오래 앉아 있기”가 아니라 “명확한 산출물이 있는 경우”에만 의미가 있다. 기공소 컨택, 전화, 답장 확인이 중요한 시기에는 주말 생산성이 낮을 수 있으므로 유동적으로 운영한다.

| 상황 | 운영 방식 |
| --- | --- |
| 발표 전주 | 토요일 근무 가능, 필요 시 일요일도 협의 |
| 파트너 컨택 집중 주간 | 평일 집중, 주말은 자료 정리 중심 |
| MVP 개발 스프린트 | 토요일 개발/검토 가능 |
| 특별한 마감 없음 | 주말 휴식 우선 |

회의에서 나온 대안인 “평일 10시 전후 출근, 주말 휴무”는 추후 운영해보고 재검토한다.

### 6.3 지각/결근/일정 변경

| 항목 | 규칙 |
| --- | --- |
| 지각 예상 | 출근 전 가능한 빨리 공유한다. |
| 결근 필요 | 전날 밤까지 공유한다. 급한 사정은 당일 공유 가능하다. |
| 외부 일정 | 수업, 병원, 미팅, 가족 일정은 미리 캘린더나 채팅에 남긴다. |
| 일정 변경 | “왜 변경되는지”와 “대체 실행 시간”을 함께 말한다. |

## 7. 회의와 회고

### 7.1 주간 회고

주 1회 회고를 진행한다. 바빠질수록 회고를 생략하지 않는다. 회고는 감정 정리용이 아니라 다음 주 실행력을 높이기 위한 운영 장치다.

권장 시간은 매주 토요일 근무 종료 전 또는 월요일 업무 시작 직후다.

### 7.2 회고 템플릿

```markdown
## 주간 회고

### 1. 이번 주 목표
- 

### 2. 실제로 한 일
- 

### 3. 잘된 점
- 

### 4. 아쉬운 점
- 

### 5. 고객/시장에 대해 새로 배운 점
- 

### 6. 팀 운영에서 조정할 점
- 

### 7. 다음 주 우선순위 3개
1. 
2. 
3. 
```

### 7.3 데일리 스니펫

매일 길게 보고하지 않아도 된다. 대신 하루가 끝날 때 아래 4가지는 짧게 남긴다.

| 항목 | 내용 |
| --- | --- |
| 오늘 한 일 | 실제 완료한 작업 |
| 막힌 것 | 결정, 자료, 사람, 개발 이슈 |
| 내일 할 일 | 가장 중요한 1-3개 |
| 도움이 필요한 것 | 상대가 봐줘야 할 것 |

## 8. 커뮤니케이션 규칙

### 8.1 카카오톡 운영

## 9. CrownOps 실행 전략

### 9.1 현재 단계의 최우선 목표

현재 목표는 완성 제품 출시가 아니라, 실제 기공소에서 쓸 수 있는 최소 기능 MVP로 문제의 강도와 지불 가능성을 검증하는 것이다.

| 우선순위 | 내용 |
| --- | --- |
| 1순위 | 파트너 기공소 1곳 확보 |
| 2순위 | 실제 케이스 기준으로 CAM 전 체크리스트 검증 |
| 3순위 | MVP를 사용 가능한 수준으로 빠르게 구현 |
| 4순위 | 1곳에서 3곳, 5곳으로 테스트 확장 |
| 5순위 | 9월 유료 전환 또는 판매 가능성 검증 |

### 9.2 초기 파일럿 제안

초기에는 “도입하세요”보다 “무료로 점검해드리고 결과를 보여드리겠습니다”가 적합하다.

> 하루 CAM 투입 전 케이스를 무료로 점검해드리고, 어떤 케이스가 바로 제작 가능하고 어떤 케이스가 확인 필요한지 리포트로 정리해드립니다.

파일럿 결과물은 다음과 같다.

| 결과물 | 내용 |
| --- | --- |
| 오늘의 케이스 상태표 | 제작 가능 / 검증 필요 케이스 분리 |
| 파일 미도착 목록 | STL 또는 필수 파일 누락 케이스 |
| 의뢰서 누락 목록 | 정식 의뢰서 확인 필요 케이스 |
| 재료·쉐이드 누락 목록 | 제작 조건 확인 필요 케이스 |
| 최종 확인 필요 목록 | 소장/책임자 확인 대상 |
| 개선 리포트 | 반복적으로 발생한 누락/불일치 유형 |

### 9.3 기능 우선순위

| 우선순위 | 기능 방향 |
| --- | --- |
| 1순위 | 파일 누락·불일치 방지 |
| 2순위 | 외부 검증 필요 케이스 분리 |
| 3순위 | 리메이크·재작업 감소 |
| 4순위 | 최종 확인 필요 케이스 분리 |

### 9.4 개발 원칙

| 원칙 | 설명 |
| --- | --- |
| 완벽보다 현장 사용 | 완전한 제품보다 실제 기공소가 써볼 수 있는 MVP를 우선한다. |
| 자동화보다 검증 흐름 | 처음부터 모든 것을 자동화하려 하지 않고, 검증 기준과 업무 흐름을 먼저 만든다. |

## 16. 최종 합의문

우리는 paraegis라는 팀으로, CrownOps를 통해 치과기공소의 제작 전 검증 문제를 해결한다. 우리의 첫 목표는 완벽한 제품이 아니라, 실제 기공소가 CAM 투입 전에 겪는 정보 누락과 불일치 문제를 작게라도 확실하게 줄이는 것이다.

우리는 의료 현장의 비의사 전문직이 더 안전하고 효율적으로 일할 수 있어야 한다는 문제의식을 가진다. 다만 외부에서는 대립의 언어가 아니라, 실무 부담을 줄이고 협업 구조를 안전하게 만드는 운영 인프라의 언어로 말한다.

두 명 체제에서는 한 사람의 침묵이 팀의 방향을 약하게 만든다. 대표는 더 분명히 말하고 설득하며, 팀원은 더 적극적으로 반론과 대안을 낸다. 우리는 좋은 사람이 되는 것보다, 서로 믿고 어려운 이야기를 할 수 있는 팀이 되는 것을 우선한다.

2026년 7월의 핵심은 파트너 기공소 확보와 MVP 개발이다. 8월에는 실제 현장 테스트를 확장하고, 9월에는 유료 전환 가능성을 검증한다. 모든 일정과 자료 제작은 이 목표에 맞춰 우선순위를 둔다.
