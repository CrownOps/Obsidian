# 2. 가장 중요한 것: ISO 18618:2025

## Interoperability of CAD/CAM systems

이 표준은 치과 CAD/CAM 소프트웨어 사이에서 **Dental Case Data와 CAD/CAM Data를 전달하기 위한 XML 형식**을 정의합니다. 2025년판이 현재 발행되어 있으며, 2026년 현재 차기 개정판도 개발 중입니다. citeturn810656search16turn810656search5

쉽게 말하면 지금 업계가 흔히 하는:

```
의뢰서 PDF
STL 파일
환자명 파일명
쉐이드 메모
임플란트 정보
CAM 작업정보
```

를 각각 따로 관리하는 대신,

```
하나의 CASE
 ├─ 케이스 정보
 ├─ 제작 정보
 ├─ CAD/CAM 정보
 └─ 관련 데이터
```

처럼 **시스템이 이해할 수 있는 데이터 단위로 교환하기 위한 표준**에 가깝습니다.

### DentalSync에 의미하는 것

DentalSync의 내부 DB를 지금부터 ISO 원문과 1:1로 구현할 필요까지는 없지만, 적어도:

```
DentalSync 내부 Canonical Case Schema
        ↓
ISO 18618 호환 Adapter
        ↓
외부 CAD/CAM 또는 타 시스템
```

구조를 잡는 것이 좋습니다.

**즉, DentalSync가 새로운 독자 규격을 만드는 게 아니라, 내부에서는 확장 가능한 공통 케이스 모델을 만들고 외부 표준과 매핑하는 방식**입니다.

# 3. 치식은 반드시 ISO 3950으로 표준화하는 것이 좋음

`ISO 3950:2016`은 치아와 구강 영역을 **두 자리 번호로 표현하는 표준**입니다. 현재 2016판이 유효하고 차기 개정판이 개발 중입니다. citeturn833567search5turn833567search3

예를 들어 DentalSync 내부에서:

```json
{
  "tooth": "11"
}
```

처럼 저장하면,

- `상악 우측 중절치`
- `#11`
- `11번`
- 의뢰서 그림에서 체크된 위치

같은 서로 다른 입력을 **하나의 표준 코드로 정규화**할 수 있습니다.

DentalSync OCR에서는 이게 꽤 중요합니다.

```
의뢰서 OCR
"상악 우측 1번"
"11"
"UR1"
치식표 체크 위치
        ↓
ISO 3950 코드
        ↓
toothSite = "11"
```

임플란트 위치 표현에는 `ISO 19429:2015`도 참고할 수 있습니다. 이 표준은 ISO 3950 체계와 연계해 임플란트 바디의 위치를 지정합니다. citeturn833567search7

# 4. 전자 의뢰서 쪽에서 가장 가까운 표준: ADA 1054

미국치과의사협회 ADA는 **Electronic Dental Laboratory Prescription** 관련 표준화를 진행해 왔습니다.

특히 최신 공식 공개자료에서는:

> **Proposed ANSI/ADA Standard No. 1054 — Electronic Dental Laboratory Prescription Forms**

가 전자 치과기공 의뢰에 필요한 데이터를 표준화하고, 치과와 외부 기공소 사이의 **안전하고 상호운용 가능한 전자 전송**을 목표로 개발 중입니다. 다만 제가 확인한 최신 공식 공개 상태인 2025년 11월 기준으로는 **Proposed Standard**였고, 최종 ANSI 표준 발행은 공식 공개자료에서 확인하지 못했습니다. citeturn810656search2

### DentalSync 입장에서는 매우 중요한 참고자료

ISO 18618이:

> **“CAD/CAM 시스템끼리 데이터를 어떻게 교환할까?”**

에 가깝다면,

ADA 1054는:

> **“전자 기공 의뢰서에는 어떤 데이터가 있어야 하는가?”**

에 더 가깝습니다.

따라서 이상적인 구조는:

```
전자 의뢰 데이터 모델
    ├─ ADA 1054 계열 참고
    ├─ ISO 3950 치식 표준
    └─ 국내 법정 의뢰서 필수 구조

CAD/CAM 데이터 모델
    └─ ISO 18618 계열 참고
```

입니다.

현재 은지님이 정리한 **환자/케이스 식별 → 치식 → 보철 종류 → 재료 → 쉐이드 → 임플란트 → 제작조건 → 첨부자료 → 검증상태 → 수정이력** 구조는 이런 국제 표준화 방향과 상당히 잘 맞습니다. fileciteturn0file7

# 5. STL·PLY·OBJ는 어디에 위치하는가?

여기서 중요한 구분이 있습니다.

**STL·PLY·OBJ는 ‘전자 의뢰 표준’이 아니라 3D 데이터 파일 포맷**입니다.

```
[케이스 데이터]
환자/케이스 ID
치식
보철 종류
쉐이드
재료
납기
임플란트 정보
        │
        ├── STL
        ├── PLY
        ├── OBJ
        └── 사진 / PDF / DICOM
```

문제는 STL 파일 자체만으로는 보통:

- 이 파일이 어느 환자인지
- 몇 번 치아인지
- 상악인지 하악인지
- 수정 전인지 최종본인지
- 어떤 의뢰서와 연결되는지

같은 **업무 맥락과 출처를 충분히 담지 못한다는 것**입니다.

그래서 DICOM에서는 STL과 OBJ를 DICOM 객체로 캡슐화해 환자·검사·원본 데이터와 추적 가능하게 연결하는 규격이 추가됐습니다. STL 캡슐화는 DICOM Supplement 205, OBJ 계열은 Supplement 208에서 다뤄졌습니다. citeturn225717search6turn225717search0turn225717search3

### DentalSync가 배워야 할 부분

굳이 MVP부터 모든 STL을 DICOM으로 변환할 필요는 없습니다.

대신 **DICOM식 Provenance 개념**은 가져오는 것이 좋습니다.

```json
{
  "assetId": "asset_001",
  "caseId": "case_20260712_001",
  "role": "maxillary_scan",
  "format": "stl",
  "sha256": "...",
  "version": 3,
  "sourceSystem": "3Shape Communicate",
  "createdAt": "...",
  "receivedAt": "...",
  "supersedes": "asset_000"
}
```

이렇게 하면 DentalSync가 잡으려는:

- 중복 파일
- 구버전 사용
- 잘못된 케이스 매칭
- 상·하악·바이트 파일 누락

을 **표준화된 방식으로 검증**할 수 있습니다.

# 6. FHIR는 전자 의뢰의 ‘범용 연결 규격’으로 볼 수 있음

HL7 FHIR에는 제가 확인한 범위에서 **치과기공물 제작의뢰 전용 국제 프로파일**이 따로 존재하지는 않습니다.

다만 기존 FHIR 리소스를 조합하면 상당히 자연스럽습니다.

|FHIR Resource|DentalSync 적용|
|---|---|
|`ServiceRequest`|보철 제작 의뢰|
|`Task`|접수·확인·CAD·CAM·제작 상태|
|`DocumentReference`|의뢰서 PDF, 스캔본, 사진 등의 참조|
|`Practitioner`|의뢰 치과의사|
|`Organization`|치과·기공소|
|`Provenance`|누가 언제 데이터를 생성·변경했는지|

FHIR의 `ServiceRequest`는 진단·치료 등 서비스를 요청하는 주문을 표현하고, `Task`는 해당 요청의 실행 과정을 추적할 수 있도록 설계되어 있습니다. `DocumentReference`는 스캔 문서, PDF, 이미지 등 외부 자료의 참조와 메타데이터 관리에 사용할 수 있습니다. citeturn227264view0turn556076search2

따라서 이것은 **공식 치과기공 FHIR 표준이라는 뜻은 아니고**, DentalSync가 장기적으로 EMR 연동을 할 때 사용할 수 있는 설계 방식입니다.

```
EMR
 │
 │ FHIR ServiceRequest
 ▼
DentalSync Case
 │
 ├─ Prescription
 ├─ STL / PLY / OBJ
 ├─ Validation Results
 └─ Manufacturing Tasks
```

# 7. 한국에서는 법이 가장 중요함

현재 국내 법 체계에서는 치과기공사가 **치과의사가 발행한 치과기공물제작의뢰서에 따라 업무를 수행**해야 하며, 시행규칙은 정해진 서식의 제작의뢰서와 **치과의사 및 치과기공소 개설자의 각 2년 보존**을 규정하고 있습니다. citeturn810656search3turn454959search0

전자문서법상 일정 요건을 충족한 전자문서는 법정 문서 보관을 갈음할 수 있는 일반적 근거가 있습니다. 다만 다른 법령에 특별한 규정이 있는 경우는 예외입니다. citeturn454959search4

특히 2023년에는 치과와 기공소를 중개하고 관련 전자 문서를 2년간 대신 보관하는 **‘전자발주서 기반 치기공물 용역중개 플랫폼’이 ICT 규제샌드박스 실증특례 대상으로 지정**됐습니다. 따라서 **“전자문서법이 있으니 우리 SaaS가 바로 법정 의뢰서를 완전히 대체할 수 있다”라고 단정하면 위험**합니다. citeturn896021search0turn896021search1

## 가장 중요한 원칙

```
법적 원본 의뢰서
        ≠
OCR로 추출된 구조화 데이터
        ≠
DentalSync의 검증 결과
```

**세 개를 분리해서 저장해야 합니다.**

예를 들어 OCR이 잘못 읽어도:

```
원본 의뢰서: A2
OCR 결과: A3
검증 결과: 원본과 불일치 가능성 → 사람 확인
```

처럼 **원본이 최종 근거로 남아 있어야** 합니다.

# 제 판단: 우선 채택해야 할 순서

### P0 — 지금 MVP 설계에 반영

1. **ISO 3950**: 치식 코드 표준화
2. **국내 법정 의뢰서 구조**: 원본·2년 보존·추적성
3. **ISO 18618:2025**: 내부 Case Schema 설계의 기준
4. **파일 hash + version + provenance**: STL/PLY/OBJ 매칭 규격
5. **ADA 1054 계열**: 전자 의뢰 필드 설계 참고

### P1 — EMR·플랫폼 연동 단계

**HL7 FHIR ServiceRequest / Task / DocumentReference**

### P2 — 고도화 단계

**DICOM 기반 3D 데이터 추적성, ISO 20896 스캔 품질, ISO 23298 밀링 품질 기준**

결론적으로 **DentalSync의 가장 강한 방향은 자체 규격을 무작정 만드는 것이 아니라, `국내 법정 의뢰서 + ADA 전자 의뢰 구조 + ISO 18618 CAD/CAM 상호운용 + ISO 3950 치식 + DICOM식 파일 추적성`을 하나의 Case Schema로 묶는 것**입니다.

이렇게 가면 신구대 협력에서도 단순히 “데이터를 주세요”가 아니라, **“현재 흩어진 치기공 데이터를 국제표준과 현장 기준에 맞춰 구조화하고, 향후 학술·교육·산업에서 재사용 가능한 치기공 데이터 규격을 공동으로 만든다”**는 협력 명분까지 만들 수 있습니다.
