# Claude Code–Obsidian MCP 연동 가이드

> [!summary] 핵심 요약
> - **Obsidian은 팀의 지식 저장소**, **Claude Code는 문서를 읽고 실제 작업을 수행하는 에이전트**로 사용한다.
> - Obsidian용 Claude Code 플러그인을 설치하면 Claude Code가 현재 열린 노트와 Vault 파일을 읽고 생성·수정할 수 있다.
> - 팀에서는 회의록, 기획서, 기술 문서, 의사결정 기록을 Obsidian에 축적하고 Claude Code로 정리·분석·업데이트하는 방식을 권장한다.

---

## 1. 도입 목적

우리 팀은 프로젝트 정보가 메신저, 개인 메모, 문서, 코드 저장소에 흩어지는 문제를 줄이기 위해 Obsidian을 **지식 저장소**로 사용한다.

Claude Code와 Obsidian을 연결하면 다음 흐름을 만들 수 있다.

```text
팀원 작성·축적
      ↓
Obsidian Vault
회의록 · 요구사항 · 연구 · 기술 문서 · 의사결정
      ↓ MCP/IDE 연결
Claude Code
검색 · 요약 · 비교 · 문서 생성 · 문서 업데이트 · 코드 작업
```

이 연동의 목표는 단순히 AI에게 파일을 보여주는 것이 아니라, 팀이 축적한 문서를 **반복 활용 가능한 프로젝트 컨텍스트**로 만드는 것이다.

---

## 2. 도입 시 얻는 이점

### 2.1 현재 작업 중인 노트를 바로 활용

Claude Code가 Obsidian에서 현재 열려 있는 문서를 확인할 수 있다.

```text
현재 Obsidian에서 열려 있는 요구사항 문서를 읽고
백엔드 작업 목록으로 변환해줘.
```

파일 경로를 매번 찾거나 문서 전체를 복사해 붙여 넣는 과정이 줄어든다.

### 2.2 여러 문서에 분산된 정보를 통합

회의록, 기획서, 연구 노트, 아키텍처 문서에 흩어진 내용을 함께 검토할 수 있다.

```text
'CrownOps MVP'와 관련된 노트를 찾아
확정된 요구사항, 미확정 사항, 충돌하는 내용을 구분해줘.
```

### 2.3 팀 문서 형식의 일관성 확보

기존 템플릿과 문서 스타일을 참고하여 같은 형식으로 새 문서를 만들 수 있다.

```text
기존 주간 회의록 형식을 참고해서
이번 회의 내용을 동일한 구조로 정리해줘.
```

### 2.4 문서와 개발 결과를 함께 유지

코드 변경 사항을 바탕으로 설계 문서나 작업 일지를 업데이트할 수 있다.

```text
이번 브랜치의 변경 내용을 분석하고
Obsidian의 API 명세와 개발 작업 일지를 업데이트해줘.
```

### 2.5 반복 업무 자동화

다음 업무를 반복적으로 처리하기 좋다.

- 일일 작업 일지 및 주간 보고서 작성
- 회의록의 결정 사항과 후속 작업 추출
- 요구사항을 개발 태스크로 변환
- 관련 노트 인덱스 생성
- 문서 내 용어와 태그 통일
- 오래된 문서와 최신 구현의 차이 분석
- 연구 자료 및 인터뷰 내용 요약

### 2.6 새 Claude Code 세션의 문맥 복구

중요한 프로젝트 정보를 Obsidian에 남겨두면 세션이 바뀌어도 빠르게 업무 맥락을 복구할 수 있다.

```text
프로젝트 개요, 최근 회의록, 의사결정 기록,
최근 작업 일지를 읽고 현재 상태를 파악해줘.
```

> [!important] RAG와의 차이
> 이 구성은 Vault에서 필요한 문서를 Claude가 조회한다는 점에서 **RAG와 유사한 사용 경험**을 제공한다.  
> 그러나 기본 구성만으로 벡터 임베딩이나 벡터 데이터베이스를 사용하는 정식 RAG 시스템이 만들어지는 것은 아니다.

## 3. 권장 활용 대상

### 적극 권장

- 프로젝트 기획서와 요구사항이 자주 변경되는 팀
- 회의록과 결정 사항을 체계적으로 남겨야 하는 팀
- 코드와 기술 문서를 함께 관리하려는 개발팀
- 인터뷰, 논문, 실험 기록이 많은 연구팀
- 매주 작업 보고서와 회고를 작성하는 팀
- 새로운 팀원이 프로젝트 맥락을 빠르게 파악해야 하는 경우

### 효과가 제한적인 경우

- Vault에 문서가 거의 없는 경우
- 파일을 단순히 한두 개 읽는 것이 전부인 경우
- 문서 정리 규칙이나 폴더 구조가 전혀 없는 경우
- 민감정보를 별도 통제 없이 한 Vault에 모두 저장한 경우

## 4. 구성 방식

### 권장 방식: Claude Code `/ide` 연결

플러그인의 공식 저장소는 Claude Code가 Obsidian을 자동 탐색하고 **WebSocket 방식으로 연결**하도록 안내한다.

```text
Obsidian
└─ Claude Code 플러그인
       ↕ WebSocket
Claude Code
└─ /ide → Obsidian 선택
```

### 예비 방식: SSE MCP 서버 직접 등록

참고 블로그에서는 다음 주소를 Claude Code에 MCP 서버로 직접 등록한다.

```text
http://localhost:22360/sse
```

이 방식도 사용할 수 있지만, 팀 표준은 설정이 더 단순한 `/ide` 방식을 우선 권장한다.

## 5. 사전 준비

각 팀원은 다음 항목을 준비한다.

- Obsidian Desktop
- Claude Code
- 사용할 Obsidian Vault
- Vault 내부의 `.obsidian` 폴더
- 커뮤니티 플러그인 사용 허용

### 설치 여부 확인

PowerShell에서 실행한다.

```powershell
claude --version
```

Vault 경로를 확인한다.

```powershell
Test-Path "C:\Paraegis"
Test-Path "C:\Paraegis\.obsidian"
```

두 명령이 모두 `True`이면 정상이다.

> [!note] 팀원별 경로
> 본 문서는 예시 경로로 `C:\Paraegis`를 사용한다.  
> 팀원은 본인의 실제 Vault 경로로 변경해야 한다.

## 6. Obsidian 플러그인 설치

이 플러그인은 Obsidian 커뮤니티 플러그인 목록에서 직접 설치하는 방식이 아니라, GitHub Release의 파일을 Vault에 넣는 방식으로 설치한다.

작성일 기준 GitHub 최신 릴리스는 `1.1.8`이다. 아래 스크립트는 고정 버전 대신 `latest` 주소를 사용한다.

### 6.1 PowerShell 설치 명령

```powershell
# 본인의 Obsidian Vault 경로
$VaultPath = "C:\Paraegis"

# 플러그인 설치 경로
$PluginPath = Join-Path `
  $VaultPath `
  ".obsidian\plugins\obsidian-claude-code-mcp"

# 플러그인 폴더 생성
New-Item `
  -ItemType Directory `
  -Path $PluginPath `
  -Force | Out-Null

# 최신 릴리스 파일 주소
$BaseUrl = `
  "https://github.com/iansinnott/obsidian-claude-code-mcp/releases/latest/download"

# 필수 파일 다운로드
Invoke-WebRequest `
  -Uri "$BaseUrl/main.js" `
  -OutFile "$PluginPath\main.js"

Invoke-WebRequest `
  -Uri "$BaseUrl/manifest.json" `
  -OutFile "$PluginPath\manifest.json"

Invoke-WebRequest `
  -Uri "$BaseUrl/styles.css" `
  -OutFile "$PluginPath\styles.css"

# 설치 결과 확인
Get-ChildItem $PluginPath
```

아래 3개 파일이 표시되어야 한다.

```text
main.js
manifest.json
styles.css
```

최종 디렉터리 구조는 다음과 같다.

```text
C:\Paraegis
└─ .obsidian
   └─ plugins
      └─ obsidian-claude-code-mcp
         ├─ main.js
         ├─ manifest.json
         └─ styles.css
```

## 7. Obsidian에서 플러그인 활성화

1. Obsidian을 완전히 종료한 후 다시 실행한다.
2. `C:\Paraegis` Vault를 연다.
3. **설정 → 커뮤니티 플러그인**으로 이동한다.
4. 제한 모드가 켜져 있다면 해제한다.
5. 설치된 플러그인에서 **Claude Code** 또는 **Claude Code MCP**를 찾는다.
6. 플러그인을 활성화한다.
7. 플러그인 설정에서 서버 상태와 포트를 확인한다.

기본 HTTP 서버 포트는 다음과 같다.

```text
22360
```

> [!warning]
> Obsidian이 종료되면 플러그인의 로컬 서버도 종료된다.  
> Claude Code에서 Obsidian 기능을 사용하려면 Obsidian을 실행해 두어야 한다.

## 8. Claude Code와 연결

### 8.1 권장 연결 방법

PowerShell에서 Vault로 이동한다.

```powershell
cd "C:\Paraegis"
claude
```

Claude Code가 실행되면 다음 명령을 입력한다.

```text
/ide
```

IDE 목록에서 다음 항목을 선택한다.

```text
Obsidian
```

연결이 완료되면 Claude Code가 현재 Vault에 접근할 수 있다.

> [!note]
> `cd "C:\Paraegis"`는 터미널의 작업 위치를 변경하는 명령이다.  
> 이것만으로 MCP가 연결되는 것은 아니며, Obsidian 플러그인 활성화와 `/ide` 연결이 추가로 필요하다.

### 8.2 예비 연결 방법: SSE 직접 등록

`/ide` 목록에서 Obsidian이 나타나지 않거나 팀 환경상 SSE 등록이 필요한 경우에만 사용한다.

Obsidian을 실행하고 플러그인을 활성화한 상태에서 PowerShell에 입력한다.

```powershell
claude mcp add `
  --transport sse `
  obsidian `
  http://localhost:22360/sse
```

등록 확인:

```powershell
claude mcp list
```

기존 등록을 제거한 후 다시 설정하려면 다음을 사용한다.

```powershell
claude mcp remove obsidian

claude mcp add `
  --transport sse `
  obsidian `
  http://localhost:22360/sse
```

> [!caution]
> 플러그인 공식 저장소는 Claude Code에 대해 `/ide` 기반 WebSocket 자동 연결을 안내한다.  
> SSE 직접 등록은 참고 가이드와의 호환 또는 문제 해결을 위한 예비 방법으로 사용한다.

## 9. 연결 확인

Claude Code에서 아래 순서로 테스트한다.

### 테스트 1: 현재 노트 확인

Obsidian에서 임의의 노트를 연 뒤 입력한다.

```text
현재 Obsidian에서 열려 있는 파일의 제목과 핵심 내용을 알려줘.
파일은 수정하지 마.
```

### 테스트 2: Vault 목록 확인

```text
현재 Obsidian Vault의 주요 폴더와 Markdown 파일을 보여줘.
.obsidian 폴더는 제외해줘.
```

### 테스트 3: 읽기 확인

```text
테스트할 노트 한 개를 읽고
내용을 세 줄로 요약해줘.
파일은 변경하지 마.
```

### 테스트 4: 생성 확인

```text
00_Inbox 폴더에 MCP-연결-테스트.md 파일을 만들고
현재 날짜와 '연결 성공' 문구를 작성해줘.
```

생성된 파일이 Obsidian 파일 탐색기에 나타나면 읽기·쓰기 연결이 정상이다.

## 10. 팀 권장 사용 방식

### 10.1 Obsidian의 역할

Obsidian에는 다음과 같은 **지속적으로 재사용할 정보**를 저장한다.

- 프로젝트 개요
- 제품 요구사항
- 고객 인터뷰
- 회의록
- 기술 설계 및 아키텍처
- 의사결정 기록
- 연구 자료와 실험 결과
- 작업 일지와 회고
- 용어집
- 업무 템플릿

### 10.2 Claude Code의 역할

Claude Code에는 다음과 같은 **실행 작업**을 요청한다.

- 여러 문서 검색 및 비교
- 결정 사항과 TODO 추출
- 문서 초안 작성
- 기존 문서 업데이트
- 문서와 코드의 불일치 분석
- 코드 구현 및 리팩터링
- 보고서와 회고 생성
- 노트 간 링크 및 인덱스 작성

### 10.3 권장 업무 흐름

```text
1. 회의·조사·결정 내용을 Obsidian에 기록
2. Claude Code가 관련 노트를 탐색
3. 요구사항·작업·위험 요소를 구조화
4. 코드 또는 문서 작업 수행
5. 작업 결과를 Obsidian 문서에 다시 반영
6. 팀원이 최종 검토
```

## 11. 팀 공통 프롬프트 예시

### 프로젝트 온보딩

```text
Obsidian에서 프로젝트 개요, 최근 회의록,
의사결정 기록, 최근 작업 일지를 읽어줘.

다음 형식으로 현재 상황을 정리해줘.
1. 프로젝트 목표
2. 현재 진행 단계
3. 확정된 결정
4. 미해결 이슈
5. 다음 작업

파일은 수정하지 마.
```

### 회의록 후속 작업 추출

```text
현재 열려 있는 회의록을 읽고
결정 사항, 담당자, 마감일, 추가 확인 사항을 표로 정리해줘.

명시되지 않은 담당자나 마감일은 추측하지 말고
'미정'으로 표시해줘.
```

### 요구사항을 개발 태스크로 변환

```text
현재 요구사항 문서를 기준으로
프론트엔드, 백엔드, 데이터, 인프라 작업으로 구분해줘.

각 작업에 다음 항목을 포함해줘.
- 작업명
- 목적
- 완료 조건
- 선행 작업
- 위험 요소
```

### 문서와 코드 동기화

```text
현재 코드베이스와 Obsidian의 API 명세를 비교해줘.

차이가 있는 항목을 먼저 보고하고,
내 승인을 받기 전에는 문서를 수정하지 마.
```

### 주간 보고서 생성

```text
이번 주 작업 일지와 회의록을 읽고
다음 형식의 주간 보고서를 새 노트로 만들어줘.

- 이번 주 완료
- 진행 중
- 주요 결정
- 문제와 위험
- 다음 주 계획
```

### 관련 노트 인덱스 생성

```text
'CrownOps OCR'과 관련된 노트를 찾아
주제별로 분류된 인덱스 노트를 만들어줘.

각 항목은 Obsidian 내부 링크 [[노트명]] 형식으로 연결해줘.
```

## 12. 안전한 운영 규칙

MCP 플러그인은 Vault 파일에 읽기·쓰기 접근을 제공한다. 따라서 팀에서는 다음 규칙을 적용한다.

### 필수 규칙

1. 대량 수정이나 삭제 전에는 변경 대상 목록을 먼저 확인한다.
2. `.obsidian` 폴더는 Claude가 임의로 수정하지 않게 한다.
3. 기존 YAML frontmatter와 `[[위키 링크]]`를 유지한다.
4. 파일 삭제와 폴더 이동은 명시적 승인 후 수행한다.
5. API 키, 비밀번호, 토큰, 인증서 등의 비밀정보를 Vault에 저장하지 않는다.
6. 환자정보, 주민등록번호, 개인정보 등 민감정보를 넣지 않는다.
7. 중요한 변경 전에는 Git 또는 별도 백업을 남긴다.
8. AI가 생성한 내용은 담당자가 사실관계와 최신성을 검토한다.

### 권장 요청 문구

```text
먼저 변경 계획과 대상 파일을 보여줘.
내 승인 전에는 파일을 수정하거나 삭제하지 마.
```

### 추천 `CLAUDE.md`

Vault 루트에 `CLAUDE.md`를 두면 Claude Code의 작업 규칙을 명확히 전달할 수 있다.

```markdown
# Obsidian Vault 작업 규칙

- 이 폴더는 팀 Obsidian Vault이다.
- `.obsidian/` 폴더를 수정하거나 삭제하지 않는다.
- 기존 YAML frontmatter를 유지한다.
- 기존 `[[위키 링크]]` 형식을 유지한다.
- 파일 삭제 및 폴더 이동 전에 사용자 승인을 받는다.
- 대량 수정 전에 대상 파일과 변경 계획을 먼저 보고한다.
- 확인되지 않은 사실을 확정적으로 기록하지 않는다.
- 비밀정보와 개인정보를 새 문서에 기록하지 않는다.
```

## 13. Vault 경로 또는 폴더명 변경 시

예시:

```text
기존: C:\기존경로\Paraegis
변경: C:\Paraegis
```

### `.obsidian`을 포함해 Vault 전체를 이동한 경우

플러그인 파일도 함께 이동되므로 일반적으로 재설치할 필요가 없다.

1. Obsidian에서 변경된 Vault 경로를 다시 연다.
2. 플러그인이 활성화되어 있는지 확인한다.
3. Claude Code에서 `/ide`를 실행한다.
4. Obsidian을 다시 선택한다.

### 문서만 옮기고 `.obsidian`을 옮기지 않은 경우

플러그인이 따라오지 않으므로 새 Vault에 다시 설치해야 한다.

### SSE를 직접 등록한 경우

서버 주소가 `localhost:22360`이라면 Vault의 절대경로를 직접 사용하지 않으므로, 일반적으로 경로 수정은 필요하지 않다. 다만 Obsidian에서 새 Vault가 열려 있고 플러그인이 활성화되어 있어야 한다.

## 14. 문제 해결

### 14.1 `/ide` 목록에 Obsidian이 없음

확인 순서:

1. Obsidian이 실행 중인지 확인한다.
2. 올바른 Vault를 열었는지 확인한다.
3. Claude Code 플러그인이 활성화되어 있는지 확인한다.
4. Obsidian을 완전히 종료하고 다시 실행한다.
5. Claude Code를 종료하고 다시 실행한다.
6. 플러그인 설정에서 포트를 확인한다.
7. 다른 프로그램이 `22360` 포트를 사용하는지 확인한다.

포트 확인:

```powershell
Get-NetTCPConnection `
  -LocalPort 22360 `
  -ErrorAction SilentlyContinue
```

### 14.2 플러그인이 Obsidian에 표시되지 않음

다음 경로와 파일명을 확인한다.

```text
<Vault>\.obsidian\plugins\obsidian-claude-code-mcp\
```

필수 파일:

```text
main.js
manifest.json
styles.css
```

추가 조치:

- 커뮤니티 플러그인 제한 모드 해제
- Obsidian 재시작
- `Ctrl + Shift + I` 개발자 콘솔에서 오류 확인

### 14.3 파일을 찾지 못함

파일 경로는 Vault 루트 기준의 상대 경로로 요청한다.

```text
올바른 예: Meetings/2026-07-20.md
잘못된 예: C:\Paraegis\Meetings\2026-07-20.md
```

MCP 도구에는 보통 다음처럼 요청하는 것이 좋다.

```text
Meetings/2026-07-20.md 파일을 읽어줘.
```

### 14.4 쓰기는 되지만 원치 않는 변경이 발생함

- Git이나 백업에서 복원한다.
- 이후 프롬프트에 승인 절차를 포함한다.
- `CLAUDE.md`에 삭제 및 대량 수정 제한 규칙을 추가한다.
- 처음에는 읽기 전용 요청으로 연결 상태를 검증한다.

### 14.5 포트 충돌

플러그인 설정에서 HTTP 서버 포트를 다른 값으로 변경할 수 있다.

예:

```text
22361
22362
```

SSE 등록을 사용 중이면 Claude Code의 서버 주소도 같은 포트로 변경해야 한다.

## 15. 운영상 한계

- Obsidian이 실행 중이어야 플러그인 서버가 동작한다.
- AI가 모든 문서를 항상 자동으로 읽는 것은 아니다.
- 문서가 많으면 필요한 범위와 검색 기준을 명확하게 지정해야 한다.
- MCP 연결이 문서의 정확성을 보장하지는 않는다.
- 잘못된 요청은 대량 수정이나 파일 손실로 이어질 수 있다.
- 팀 동시 편집과 버전 관리는 MCP가 아니라 Git, Obsidian Sync 등 별도 도구가 담당한다.
- 이 플러그인은 Obsidian 및 Anthropic의 공식 내장 기능이 아닌 커뮤니티 프로젝트이므로 업데이트 상태와 보안 위험을 정기적으로 확인해야 한다.

## 16. 팀 도입 권장안

### 1단계: 개인 테스트

- 샘플 Vault 또는 테스트 폴더로 연결
- 읽기, 검색, 신규 노트 생성만 검증
- 기존 문서 대량 수정은 금지

### 2단계: 문서 규칙 표준화

- 공통 폴더 구조 정의
- 회의록 및 작업 일지 템플릿 정의
- 태그와 내부 링크 규칙 정의
- Vault 루트에 `CLAUDE.md` 추가

### 3단계: 팀 업무 적용

- 회의록 TODO 추출
- 주간 보고서 생성
- 요구사항과 개발 태스크 연결
- 코드와 기술 문서 동기화

### 4단계: 자동화 확대

- 문서 인덱스 자동 생성
- 오래된 문서 탐지
- 변경된 코드 기반 문서 갱신
- 연구 및 인터뷰 자료 통합 분석

> [!tip] 도입 원칙
> 처음부터 모든 문서를 AI가 자유롭게 수정하게 하기보다,  
> **읽기 → 초안 생성 → 변경 계획 검토 → 제한적 수정** 순서로 권한을 확대한다.
